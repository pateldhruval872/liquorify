### 1.1 How each expected answer was written

Every expected answer is written in the scripts, and the scripts were committed before the recorded runs: at `ba8fd69` for the first pair, and at `9f512ab`, with G-40's, for the second.

- **From Spree's code and the earlier records.** A request the caller's role does not allow answers 403 `access_denied` naming the missing permission. A change or removal of a record the caller may not change answers 404 `record_not_found`, because Spree looks the record up among those the caller may change before it checks the permission. Part 1's refusal check had observed the same 23 answers of 403 and 10 of 404, and part 2's the same 25 answers of 403. The Store API answers 401 `authentication_required` without a customer, and 404 for another customer's record, which each endpoint looks up among the caller's own.
- **G-40's, from Spree's code.** Saving the store goes to the permission gate without looking a record up, so the settings viewer and the order manager are each refused with 403 `access_denied` naming `write_settings`. Saving a policy, a channel or a market looks the record up first, among those the caller may change, so the settings viewer, who may read them, is answered 404 `record_not_found`, as for the payment provider below. A development trial answered each as written, and none was changed after it.
- **One expectation corrected after a development trial.** For the developer settings viewer switching a payment provider off, the script first expected 403 `access_denied` naming `write_settings`. A development trial, on a database the trials reused, answered 404 `record_not_found`. Spree's code explains it: the viewer may read payment providers but not change them, and the record lookup for a change runs before the permission check, as for the 10 answers of 404 above. The expectation was corrected to 404 `record_not_found`, with the reason in the script, before the first recorded runs. Batch 2 recorded that the interface shows this switch enabled for the viewer (B4, B5); §5 records the answer.
- **The storefront's answers, from its code.** A server action that reads one record answers `null` when the Store API refuses; one that changes a record answers `{ success: false }` with the Store API's message ("Address not found", "Credit card not found"), or "Not authenticated" for a guest; a list answers its empty fallback for a guest. A guest asking for an account page, or for an action that only account pages carry, is sent to sign in by the storefront's middleware before any of its code runs. Each was seen once while finding how to send the actions, before the script was written.
- **Requests that name no record.** Reading or changing the profile and the account's lists cannot name another customer's record. For them, the other customer's answer must be 200 with their own account, carrying nothing of the first customer's. For "change the profile", the request also names the first customer's id, and the first customer's profile is read back unchanged. These 11 answers are not refusals: they show the endpoint acts only on the caller's own account.

The development trials ran on reused databases and are not evidence.

## 4. Nothing leaks (criterion 9)
