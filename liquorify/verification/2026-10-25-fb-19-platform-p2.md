## 2. Results

### 2.1 API keys (criterion 1)

On the API keys screen the admin made a publishable key, and a secret key with only "View Products" ticked. The script then used each key from outside the browser.

| Request | Answer |
|---|---|
| Store API products, with the publishable key | 200 |
| The same, with no key | 401 |
| Admin API products, with the secret key | 200 |
| Admin API, creating a product with the secret key | 403 |
| Admin API orders, with the secret key | 403 |
| Admin API products, with the publishable key | 401 |

The admin then revoked each key on the screen, through its row menu and the confirmation. Both rows show "Revoked", and the same two reads that worked before are now refused with 401.

**Result:** PASS ([captures](#8-evidence)).

### 2.2 An OAuth client and the consent page (criterion 2)

On the OAuth clients screen the admin registered a client whose callback is a receiver on this machine, at a loopback address over plain http, which Spree accepts for a client on the same machine. The browser test then did what a client does: it sent the browser to Spree's authorization endpoint with a state and a PKCE challenge, asking for `read_products`. Spree sent it on to the dashboard's consent page, `/{store}/oauth/authorize`, which named the client and the permission.

- **Approve.** After "Allow access" the browser reached the callback with a code and the state it sent. Exchanging the code with its verifier answered 200, a Bearer token with scope `read_products` that lasts 7,200 seconds. The token read products (200) and was refused for orders and for creating a product (403 each). Spree's revocation endpoint answered 200, and the token was then refused (401).
- **Deny.** After "Cancel" the callback received `error=access_denied`, an error description and the same state, and no code.
- **Codes.** The same code exchanged a second time was refused (400, `invalid_grant`). A second approval's code was refused without its verifier (400, `invalid_request`) and with another verifier (400, `invalid_grant`).

**Result:** PASS. This is the approval on the consent page in a browser test that the owner assigned to P2 (G-30).

### 2.3 Allowed origins (criterion 3)

The script asked for a customer password reset through the Store API three times, each naming a redirect address. It read the result from the webhook delivery of `customer.password_reset_requested` (§2.5). Each request was answered 202.

| Redirect address named | Carried in the event |
|---|---|
| On a new origin, before it was added | No: the event has no `redirect_url` |
| On the same origin, after the admin added it on the allowed origins screen | Yes, unchanged |
| On another origin | No |

**Result:** PASS. Cross-origin browser access is configured by the host application, not by Spree's engine, so P2 does not check it.

### 2.4 The agent server (criterion 4)

On the agent server gem's own test app, with the dashboard served against it, the admin chose "Connect an agent" on the AI agents screen, kept Claude, and chose "Continue". The sheet showed the store's agent server address and the client ID. The script then stood in for Claude's terminal client, which the sheet's other tab sets up:

1. It called the address the sheet showed with no token. Spree answered 401, with a challenge naming its discovery document and a message saying to sign in.
2. It followed the discovery documents to the authorization endpoint, and asked for "view products" and "manage products", naming the resource the document gave.
3. On the consent page, which named Claude and both permissions ticked, the admin unticked "Manage Products" and allowed access.
4. The callback received a code and the same state. The exchange answered 200 with scope `read_products` only.

Then, with the token, from outside the browser:

| Step | Answer |
|---|---|
| Start a session | 200. The server names itself `spree-admin` and offers tools |
| List the tools | Eight: `create_export`, `create_import`, `describe_import_mapping`, `describe_resource`, `get_import_status`, `get_resource`, `propose_import_mapping`, `search_resources`. No tool that needs a permission the grant lacks, such as `upload_file`, which needs "manage products" |
| Search products for one the admin created through the Admin API | The product, by its ID, and nothing else |
| Search orders | Refused: "You do not have permission to read orders." |
| Call `upload_file`, which was not offered | Refused by the protocol: "Tool not found: upload_file" |
| Start a products import through `create_import`, which is offered | Refused: "You do not have permission to import products." |
| The same product search with no token | 401 |

Back on the AI agents screen, Claude's card lists the admin's connection with the access "View Products". The admin revoked it there, and the token was then refused (401).

Tools that take the resource as an argument, such as `search_resources` and `create_import`, are offered to any grant that may read something. They check the grant on each call, as the orders search and the products import show (§4).

**Result:** PASS.

### 2.5 Webhooks (criterion 5)

Two receivers on this machine recorded every request: one answering 200, and one answering 500 to everything.

1. **An endpoint and its secret.** On the webhooks screen the admin made an endpoint for the first receiver, subscribed to `product.updated` and `customer.password_reset_requested`. After "Create" a dialog showed the signing secret, 64 hexadecimal characters, and said it would not be shown again. The script kept it in memory. The endpoint's page, captured afterwards, shows the address and no secret. PASS.
2. **The test delivery.** "Send test" on the endpoint's page reached the receiver. Its signature verifies with the secret, and the page lists the delivery as succeeded with response 200. PASS.
3. **Real events.** A product published through the Admin API reached the receiver as `product.updated`; the password resets of §2.3 arrived as `customer.password_reset_requested`. Each signature verifies, each carries its event name in a header and in its payload, and each payload has the Store API's shape: `id`, `name`, `created_at`, `data` and `metadata`, with prefixed IDs (`prod_…`, `cust_…`). The product's fields are all in the Store API's own answer for that product. A customer created through the Admin API was not delivered, and nothing outside the two subscribed events reached the receiver. PASS.
4. **Retries and automatic disabling.** For an endpoint pointing at the failing receiver, the first failed delivery was sent again about three seconds later with the same payload. After 15 deliveries had failed in a row, Spree marked the endpoint inactive with the reason "Automatically disabled after repeated delivery failures", which its page shows with a "Re-enable" button. EM-S-07 reached the store's staff address in the mail folder, with the subject "Webhook endpoint disabled:" and the endpoint's name. PASS.
5. **The storefront's receiver.** The storefront at `321fa1c` was started with the secret of an endpoint subscribed to `order.placed`, `order.canceled` and `order.fulfilled`. Two orders were placed through the Admin API, as Spree's own dashboard tests place theirs; one was shipped and the other canceled. Spree recorded each of the four deliveries as succeeded, the storefront answering `{"received":true,"handled":true}`. The storefront wrote the order confirmation, shipment and cancellation emails (EM-SF-01, EM-SF-03 and EM-SF-02), each naming its order. A delivery with a forged signature was refused with 401 "Invalid signature", one with no signature with 401 "Missing signature headers", and neither wrote an email. PASS. This is the webhook part of G-16.

### 2.6 Tracing of webhook deliveries (criterion 6)

The tracing gem's test app exported spans to the script's collector. The script made an endpoint for its receiver through the Admin API, sent the test delivery and created a product, whose `product.created` event the endpoint is subscribed to.

| | Test delivery | `product.created` |
|---|---|---|
| The delivery's span | `spree.webhook.deliver webhook.test`, kind client, from Spree, with the event, the receiver's host and the response status as attribute names | `spree.webhook.deliver product.created`, the same |
| Headers the receiver got | `traceparent` only: no `tracestate` and no `baggage` | The same |
| What `traceparent` names | The delivery's trace, with the outgoing HTTP request inside the delivery span as its parent | The same |
| Other spans in the delivery's trace | The job's run, the database queries and the outgoing HTTP request | The same |
| The request that caused it | In another trace, reached by following one span link: the job links to the request that queued it | Reached by following two links: the request, then the event's own job, then the delivery's job |

**Result:** PASS. A delivery is recorded as a span, and its request carries the trace context to the receiver. These traces also show job runs and outgoing HTTP requests, two of the layers P1 did not see.

## 3. Nothing leaks (criterion 7)

- Keys, secrets, tokens, codes, verifiers and passwords stay in the scripts' memory. The admin passwords of the browser-test data and of the agent server gem's test app, the storefront's publishable key and its endpoint's secret were passed in at run time from private files on this machine, and are recorded nowhere.
- The results keep statuses, field names, error texts and whether values matched, never the values.
- Every screenshot paints out the key and secret columns, the secret dialog, and every address on this machine. The first recorded runs, at `ef37108`, showed the browser-test data's own local origin on the allowed origins screen; `871a551` paints it out, and the runs recorded here are at that revision.
- The OAuth client IDs and the agent's client ID appear in captures, as in batch 2's. They are public identifiers: these clients have no secret.
- A secret search over this branch found no key, token, client secret or webhook secret.
