# FB-19 batch 9, storefront cart and checkout

**Claim.** [Batch 9](../work-items/fb-19-batch-storefront-cart-and-checkout.md) reproduces what the storefront already has for buying: the cart drawer, the cart page, checkout with its address, delivery and payment steps, the page that finishes a payment after a provider's extra check, the order placed page, the checkout address editor and the order confirmation emails. It gives the 13 new components and the cart drawer's missing states 81 Storybook stories, with a reference image at each of the storefront's two widths. It captures those screens on the running storefront in each meaningful state, as a guest and a signed-in customer, in two markets, and under batch 7's checkout settings saved through the dashboard. It places orders with Spree's Check method and with a gift card that covers the whole total, compares the batch's stories, and four it reuses, with the same components on the running screens in 30 cases, runs Spree's own specs for the cart, checkout and order endpoints and for stock held during checkout, and runs the storefront's own cart, product and checkout tests. ## 13. Limitations

- **One run of each capture.** Each state was captured on one run, or on the rerun that replaced a failed or disturbed one (§2.1); the capture scripts' assertions held on that run. They are not browser tests (G-75).
- **One lane, one machine.** The running screens are this lane's storefront and browser-test server, with Spree's sample catalog and what the scripts added. Another database, another store or a real deployment was not tried.
- **No real provider.** Nothing about Stripe, Adyen or PayPal, express checkout or a saved card is verified (§5, G-76). The storefront's Stripe checkout test passed in CI against Spree's published image, not against this repository's backend (FB-06).
- **Two runs overlapped.** Part of the comparison run overlapped the capture run on the same server, and both redeemed the same gift cards, so applying a code in one run took it off the other run's cart (B19). Every capture and case that applies a code now asserts that it was applied, and those that ran during the overlap were run again (§2.1, §4).
- **The capture setting left at Manually.** The `capture-manual` step failed twice before it passed, and each failure left the store charging manually, since the step put the setting back only at its end. The four orders placed before it passed, R1003 to R1006, were placed while the store charged manually and kept their Check payments pending; none is used as evidence here. The step now puts the setting back even when it fails; the store read "checkout" when the runs ended.
- **Long prefetches.** Once the cart has an item, the storefront's prefetches of other pages can stay open for half a minute, so the scripts wait for what they need on the page rather than for the network to settle.
- **The comparison is diagnostic.** It reads computed styles and puts images side by side; it does not judge fidelity, which is the reviewer's, here under the owner's delegation (§15).
- **Not reported upstream.** Nothing found is reported to Spree, by the owner's standing instruction.
- **Tenant isolation** is FB-03's validation, NOT_RUN here (§3.3).
