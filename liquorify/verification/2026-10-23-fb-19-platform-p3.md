**Why the dashboard's own app and not the starter.** The work item says to load the example into the dashboard starter. The starter finds plugins among its own dependencies, so loading the example there means adding it to the starter's `package.json` and lockfile, which are Spree's files. Spree's dashboard app instead has a switch that turns on the same discovery for the example, and the example's README says it "exercises the exact path a real host uses". P3 used the switch and changed nothing. CI type-checks and lints the dashboard of a project scaffolded from the starter, but no starter runs with a plugin, so the starter's integration is not verified.

**The one file the build rewrites.** Building with the switch regenerates `packages/dashboard/src/routeTree.gen.ts` with the example's two routes, as the starter's configuration says a host's build does. The change is kept as [route-tree.diff](evidence/2026-10-23-fb-19-platform-p3/route-tree.diff), and Spree's file was put back with `git checkout` before anything was committed.

## 3. What this means

**What P3 supports.** The frontend plugin mechanism, as the example exercises it: the dashboard discovers the example, switches it on, and shows its navigation entry, its two file routes, its slot entry, its column on a stock table and its translations, none of which a dashboard without it shows. And the generic slot component rendering a plugin's entry on a running screen.

**What P3 does not verify:**

- **The starter app's integration.** P3 used the dashboard's own switch, not a starter with the plugin among its dependencies (§1).
- **Slot entries on staff screens.** The slot entry is on the product page. The example registers nothing in the staff screens' own slots, and no stock screen registers an entry anywhere.
- **The brand backend, which does not exist.** The brand screens show data only when the browser answers for one (row 4); the server answers "not found" (row 2).

**CAP-11-07.** Before P3 it was PARTIAL, on unit tests and a type-checked scaffold. If the owner accepts this corrected record, CAP-11-07 can be PASS for the frontend plugin mechanism within the limits above. That is the owner's call.

**G-09.** Part 1's slot (CMP-CORE-34) was deferred to this step because no stock screen registers an entry, so it was never seen on a running screen. Row 5 shows the slot component rendering an entry on a running screen, the product page, which is generic slot rendering. It does not show an entry in a staff screen's slot. G-09 stays PENDING until the owner answers whether this evidence closes it.

## 4. Defects found

None in Spree. Two faults in this record's first version were found by the owner's review, both in the script and the claims, and both are corrected (§6):

1. The check of the Brands page as the server answers it recorded the server's answers and whether the table settled, but asserted neither, so it would have passed on a server error.
2. The control claimed that the stock dashboard shows none of the example's entries, but checked only its navigation entry and its product page card.

While the script was first written, one capture failed because it expected the Brands page's address without the table's query string, which the table adds; the script was corrected before the recorded runs.
