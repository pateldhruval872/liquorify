**Why the dashboard's own app and not the starter.** The work item says to load the example into the dashboard starter. The starter finds plugins among its own dependencies, so loading the example there means adding it to the starter's `package.json` and lockfile, which are Spree's files. Spree's dashboard app instead has a switch that turns on the same discovery for the example, and the example's README says it "exercises the exact path a real host uses". P3 used the switch and changed nothing. CI type-checks and lints the dashboard of a project scaffolded from the starter, but no starter runs with a plugin.

**The one file the build rewrites.** Building with the switch regenerates `packages/dashboard/src/routeTree.gen.ts` with the example's two routes, as the starter's configuration says a host's build does. The change is kept as [route-tree.diff](evidence/2026-10-23-fb-19-platform-p3/route-tree.diff), and Spree's file was put back with `git checkout` before anything was committed.

Every label the example adds, "Brands", "New brand", "Brand" and "No brand assigned.", comes from its own translation file, merged into the dashboard's, so the translations entry its README names shows on each of these screens.

**One thing to note.** In row 2 the server refuses the request, and the table shows its empty message, "No brands yet", rather than an error. That is how Spree's table presents a failed list request for this example. It is recorded here as seen, not as a defect: the example says a real plugin ships its own backend, and P3 checked no other table's failure.

## 3. What this means

If the owner accepts this record, CAP-11-07 can be PASS for the plugin mechanism within those limits. That is the owner's call.
