# FB-19 catalog and pricing batch, part 1: evidence

The captures, comparisons, FL-04's storefront check and backend results behind the [verification record](../../2026-11-02-fb-19-batch-catalog-and-pricing-part-1.md). They come from the scripts in `packages/liquorify-storybook/fidelity/` (`screens.spec.ts`, `compare.spec.ts` and `fl-04-storefront.spec.ts`, with the data `catalog.ts` and `staff.ts` add) and from Spree's own specs. A successful run of the scripts only shows that each state could be reached and captured. Whether each story matches its screen is the owner's judgement from these files.

| What | Revision |

The captures and FL-04 ran from `db550f1d`, with the scripts as `9c4d8cbb` commits them unchanged; the comparison ran from `9c4d8cbb`, which has the corrected stories of `073d355f`, and its fill handle's chosen price case again at `ea6a8335`, with the story as `fa78b4d8` corrected it |
| Running screens, the storefront and Spree's specs | Spree's code at `01a0365`, which the pull request does not change: the built admin dashboard against the dashboard browser tests' own Rails server and fixtures, with Spree's sample catalog loaded into its database, and the storefront at `8865498`, built for production against the same server |
| Browser | The pinned Playwright 1.64.1 image. Captures at 1280 by 960 pixels, and 390 by 844 for the four phone states; comparisons at 1280 by 800, and 1280 by 2400 for the cases taller than the window. Captures follow the system's light or dark setting; none stores a choice of theme |

**Image format.** Every image here is lossless WebP, converted from the PNG each script wrote. Every converted image was checked pixel for pixel against its PNG, and none differs. The reference images the visual check compares against stay PNG, in `packages/liquorify-storybook/visual/__screenshots__/`.

**Data.** The screens show the browser tests' data and Spree's sample catalog, loaded with Spree's sample data task, plus the products, files, metadata, roles and teammates the scripts add through the Admin API (record §1). Teammates use `example.com` addresses. Each capture's store is written as `<store>` in its notes, and the storefront's address as `<a local address>`. **No key, token or password is recorded:** the scripts read the storefront's publishable key through the Admin API and keep it in memory, and no capture shows a key. The comparison's key mask hides any code drawn in a card on both sides, which in part 1 hides the metadata card's keys and nothing else.

## Screens, by state and variant

Each state of the six screens as it runs, light and dark. The variant names who is signed in:

- **admin** is the browser tests' admin, who holds every permission.
- **catalogViewer** is a teammate whose role, added by `fidelity/staff.ts`, reads `products`, `publishing`, `media`, `product_types` and `stock` and writes nothing.
- **merchandiser** is a teammate with Spree's merchandiser template's role, which writes products, categories, collections and stock and holds nothing on publishing, media or product types.
- **orderManager** is a teammate with the order manager template's role, which holds none of part 1's permissions; each of its captures is a direct visit to the page's address.

"Reached by" says how a request was answered or held in the browser, from each capture's note. "YouTube's still" means only the picture YouTube serves for the sample video link was answered with a local one, so that no request left the local servers; the state itself is the server's.
