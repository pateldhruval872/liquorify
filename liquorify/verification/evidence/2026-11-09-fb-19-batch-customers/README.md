# FB-19 batch 10, customers in the dashboard: evidence

The captures, comparisons, emails, the SD-45 trace and the backend results behind the [verification record](../../2026-11-09-fb-19-batch-customers.md). They come from the scripts in `packages/liquorify-storybook/fidelity/`: `screens-batch-10.spec.ts` and `compare-batch-10.spec.ts`, with the data `customers.ts`, `orders.ts` and `staff.ts` add; `customer-emails.rb` and `order-emails.spec.ts` for the emails.

**Revisions.**

| What | Revision |
|---|---|
| Stories and scripts | The pull request the verification record names, branch `claude/project-thread-d402n2`. The captures, comparison and email captures ran from the branch's working tree on `05b7c95b`, and their notes name it |
| Running screens and Spree's specs | Spree's code at `05b7c95b`, where the branch starts, the same as at `main`'s `44be970f`; the pull request does not change it. The built admin dashboard against the dashboard browser tests' own Rails server and fixtures |
| Browser | The pinned Playwright 1.64.1 image. Captures at 1280 by 960 pixels, and 390 by 844 for the one phone capture; a customer page captured whole grows the window to the page's height, and the phone capture is the whole page. Comparisons at 1280 by 800, or taller where a case names it. Emails at 390 and 1280 pixels wide. Captures follow the system's light or dark setting; none stores a choice of theme |

**Image format.** Every image here is lossless WebP, converted from the PNG each script wrote. Every converted image was checked pixel for pixel against its PNG, and none differs. The reference images the visual check compares against stay PNG, in `packages/liquorify-storybook/visual/__screenshots__/`.

**Data.** The screens show Spree's sample customers, the browser tests' data, batch 8's orders, and the group, customer field, customers, addresses, registration numbers, credits, roles and teammates the scripts add through the Admin API (record §1). Every name the scripts add is invented, and every email is at `example.com`. The customer export was read for its outline only: each `export/<variant>-<theme>-file-outline.json` holds the file's name and what each section holds, never the file. The emails' tokens are replaced by `<token>` and the test app's address by `<site>`.

## Folders

| Folder | Holds |
|---|---|
| `screens/<screen ID>/<state>/` | `<variant>-light.webp` and `<variant>-dark.webp` for each variant, and `<variant>-<theme>.json`: the screen, the state, the variant's role, the theme, the revision, the path, the window's size, whether the page was captured whole and how tall, how a request was answered or held to reach the state (`intercepted`), the earlier batch's hand-off the capture shows (`handOff`), whether the page settled, and every request blocked because it would have left the local servers (none) |
| `comparison/<case>/` | `<theme>-side-by-side.webp`: the running screen on the left and the story on the right; `<theme>-styles.json`: the computed styles of every distinct element on both sides, how many elements were compared, those found on one side only, and every style that differs |
| `emails/` | `<email>-390.webp` and `<email>-1280.webp` for each email, and `emails.json`: each email's subject, parts and links |
| `sd-45/` | `address-defaults-check.txt`: the customer's default addresses after each address change sent through the Admin API (record §5.2) |
| `backend/` | `api-specs.json`, `core-specs.json` and `email-specs.json`: every example of Spree's specs for the batch's endpoints, models, workflows and mailers, with its file, line, description and result. The 91 integration examples are written through rswag's helpers, so RSpec reports the helper's file for them; each carries its own spec file instead, from its example identifier, with no line |
