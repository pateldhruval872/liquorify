# FB-19 platform batch, step P4, the real providers

**Claim.** Step P4 of the [platform batch](../work-items/fb-19-batch-platform.md#p4-the-real-providers-stripe-easypost-and-meilisearch) checks Spree's Stripe, EasyPost and Meilisearch providers against Stripe's and EasyPost's test modes and a local Meilisearch server. Every check, its expected result and its closing condition were recorded in the work item before any script was written ([P4's checks](../work-items/fb-19-batch-platform.md#p4s-checks-recorded-before-implementation)). The checks are Liquorify's own scripts in `packages/liquorify-storybook/fidelity/`:

- `p4-stripe.spec.ts`, part 1 (4.1 to 4.5)
- `p4-storefront-stripe.spec.ts`, part 2 (4.6 to 4.10)
- `p4-easypost.spec.ts`, part 3 (4.11 to 4.17)
- `p4-payouts.spec.ts` and `p4-meilisearch.spec.ts`, part 4 (4.18 to 4.21, and 4.23)
- `p4.ts`, what they share, and `providers/Gemfile`, which adds the three provider gems to the test server's bundle

They change nothing in Spree's code, tests or workflows, and nothing in the storefront's code.

## 1. How the checks ran

- **Revision.** Scripts at `917cdcc3`; Spree's code and the storefront's code unchanged from `main` (`fd711171` for the backend). A later commit changes one comment in `p4-easypost.spec.ts` and nothing else (§1.2).
- **Runs.** Run 1 from about 01:14 to 01:23 UTC and run 2 from about 01:25 to 01:33 UTC on 2026-11-11. Before each run the server, Meilisearch and the storefront were stopped and started again, Meilisearch with an empty index and the server with a fresh database. The two runs gave the same pass, fail and not-run result for every check.
- **The server.** The dashboard browser tests' own Rails server (`stack.spec.ts`), with the provider gems added by `LIQUORIFY_PROVIDERS=1` and the search provider set to Meilisearch when `MEILISEARCH_URL` is set. An error reporter logs every error Spree reports, so a refusal Spree swallows is still seen.
- **Keys.** Spree's settings and the scripts carry placeholder keys only (`sk_test_placeholder`, `pk_test_placeholder`, `EZTK_placeholder`). The environment's proxy replaces them with the owner's test keys on every request to `api.stripe.com` and `api.easypost.com`. Every Stripe and EasyPost answer was checked to be in test mode. No key was printed, written or committed. Stripe's test publishable key, which the storefront's payment form needs in the browser, was read from the environment at build time; it is in the storefront's local build output and nowhere else.
- **Meilisearch.** Its official release binary, version **1.56.2**, run locally. Version 1.12.8 was tried first and every Store API product listing failed with "invalid float literal" (from Spree's filter on `available_on`), so the runs used 1.56.2. Spree names no minimum Meilisearch version; this is an observation for whoever chooses one, not a defect.
- **The storefront.** Built for production from the storefront's `main` and served on port 3001 against the same server. The checks drive it from Liquorify's scripts in the backend repository, not from the storefront's repository as the work item said; the storefront's code is unchanged.
- **Webhooks.** Neither provider can reach the server. The work item said the scripts would read the real events from each provider's event list. That was done in spirit for trackers only:
  - **Trackers (4.17):** each tracker is EasyPost's own test tracker, created through its API, and its object is relayed in an event envelope the script composes, signed with the integration's secret. **Relayed, not delivered by the provider.**
  - **Refunds (4.15):** EasyPost's test mode never completes a refund. Its own refund list holds only `submitted` and `rejected` refunds, and its event list holds no refund event. The `refund.successful` event 4.15 relays is composed by the script in EasyPost's published shape. **Composed and relayed, not sent by EasyPost.**
- **Deliberate failure.** With Meilisearch stopped and nothing else changed, 4.23 fails, as it should. The other checks' failing assertions are shown to bite by the failures in §2.

### 1.1 Changes during the development trials

- The payouts checks waited for the marketplace settings' hint and option before reading them; a freshly started server showed them a moment late. Their expectations are unchanged.
- The scripts reused a saved marketplace from an earlier trial, which a fresh database no longer holds. The run script now deletes that saved state first.
- EasyPost's test account limits how fast it may be called. Requests it limits are retried after a pause, and an order is drafted again until EasyPost's rates have arrived.

### 1.2 After the runs

One comment in `p4-easypost.spec.ts` said 4.15 relays "the event EasyPost sends". It now says the event is composed. No code or assertion changed.

## 3. Why the storefront's payments are blocked

The environment's proxy adds the Stripe secret key to **every** request to `api.stripe.com`, including the requests the shopper's browser makes with the publishable key. A request carrying only a publishable key was answered as if it carried the secret key. Stripe.js confirms a payment with a parameter, `expected_payment_method_type`, that Stripe accepts only from a publishable key, so Stripe refuses every payment the browser sends. This is the environment, not Spree or the storefront: 4.2, 4.3 and 4.5 pay the same Stripe account successfully from the server.

The checks still assert the intended result and fail at the refusal, which each records. They pass only in an environment where the browser's own requests to Stripe are left alone. The owner was asked how to handle this; until then they are recorded as BLOCKED.

## 4. Defects

The baseline audit numbered these; each is held for the owner's answer, and the proposed severities are the audit's.

| Defect | What happens | Where seen | Proposed severity |
|---|---|---|---|
| SD-97 | Stripe refuses to register Spree's payment webhook endpoint for a store whose URL has no scheme. `PaymentMethod#webhook_url` builds the address from the store's URL as saved, and Spree's own seeds and factories save it without one. Spree reports the refusal to its error reporter and saves the method anyway, so a merchant sees nothing wrong. **A store whose URL is saved with `https://` registers both endpoints** (4.1's control, in both runs), so this affects stores saved without a scheme, which includes Spree's sample setup | 4.1, both runs | Medium |
| SD-98 | When a Store API cart cannot complete after a failed payment, the 422 message is a Ruby hash printed as text (`{:code=>"validation_failed", …}`) instead of a readable message | 4.4, both runs | Low |
| SD-99 | EasyPost's refund confirmation is never applied. `SpreeEasyPost::Integration#parse_webhook_event` handles only `tracker.*` events, and the refund confirmation's handler has no caller, so a refunded label stays Refund requested | 4.15, both runs, with a composed event (§1) | Low |
| SD-100 | Stripe refuses to create the seller's Connect account | 4.19, both runs | High |

**SD-100, what Spree's code shows and what it does not.** Spree's request (`SpreeStripe::Gateway::Connect#connect_account_params`) creates an Accounts v1 account through `Stripe::Account.create`, with the platform paying Stripe's fees and carrying payment losses (`controller: { fees: { payer: 'application' }, losses: { payments: 'application' }, stripe_dashboard: { type: 'express' } }`). Stripe's answer names a change to the request: use Accounts v2 with Stripe as the losses collector. Whether a Connect setting on the platform's Stripe account would accept the v1 request as it is was **not** tested, because the account's Connect settings were not changed. If such a setting lets it through, the refusal is an owner action on the Stripe account rather than a defect in Spree; if not, it is a defect in Spree's request.

## 5. Observations

- **The international label's price.** The buy confirmation quoted $21.86 and the label was bought at $128.03 for the same rate. This is EasyPost's test mode; it is not known whether live mode does the same.
- **EasyPost's rate limit.** When EasyPost limits its test account (429), Spree drops the EasyPost delivery method without a word, and the order gets no delivery method. The scripts retry; a shop would show no EasyPost rate.
- **Geocoding.** Spree's address geocoding is refused by this environment's proxy (403). It is reported to the error reporter and changes nothing else.
- **Database search replaced.** With Meilisearch set, the store's product search runs only on Meilisearch; with Meilisearch stopped, product listings fail.
- **Meilisearch 1.12.8** fails every product listing with Spree's filter (§1).
