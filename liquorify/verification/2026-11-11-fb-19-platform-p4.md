# FB-19 platform batch, step P4, the real providers

Every check, its expected result and its closing condition were recorded in the work item before any script was written ([P4's checks](../work-items/fb-19-batch-platform.md#p4s-checks-recorded-before-implementation)). ## 1. How the checks ran

- **Revision.** Scripts at `917cdcc3`. Spree's code is unchanged from `main` at `fd711171`, and the storefront's code is unchanged from its `main`. Two later commits change only a comment and a blank line (§1.2).
- **Runs.** On 2026-11-11, run 1 ran from about 01:14 to 01:23 UTC and run 2 from about 01:25 to 01:33 UTC. Before each run, the server, Meilisearch and the storefront were stopped and started again: Meilisearch with an empty index, and the server with a fresh database. Every check had the same status in both runs.
- **The server.** It is the dashboard browser tests' own Rails server (`stack.spec.ts`). `LIQUORIFY_PROVIDERS=1` adds the provider gems, and setting `MEILISEARCH_URL` makes Meilisearch the search provider. An error reporter logs every error Spree reports, so a refusal that Spree swallows is still seen.
- **Keys.** Spree's settings and the scripts carry placeholder keys only: `sk_test_placeholder`, `pk_test_placeholder` and `EZTK_placeholder`.
  - The environment's proxy replaces them with the owner's test keys on every request to `api.stripe.com` and `api.easypost.com`.
  - Every Stripe and EasyPost answer was checked to be in test mode.
  - No key was printed, written or committed.
  - The storefront's payment form needs Stripe's test publishable key in the browser. It was read from the environment at build time, and it exists only in the storefront's local build output.
- **Meilisearch.** The runs used its official release binary, version **1.56.2**, run locally. Version 1.12.8 was tried first: every Store API product listing failed with "invalid float literal", from Spree's filter on `available_on`. Spree names no minimum Meilisearch version. This is an observation for whoever chooses a version, not a defect.
- **The storefront.** It was built for production from the storefront's `main` and served on port 3001 against the same server. Liquorify's scripts in the backend repository drive it, not scripts in the storefront's repository as the work item said. The storefront's code is unchanged.
- **Webhooks.** Neither provider can reach the test server, and **no provider delivered any callback to it**. The work item said the scripts would read the real events from each provider's event list. That was not done as written:
  - **Trackers (4.17).** Each tracker is EasyPost's own test tracker, created through EasyPost's test API. The script wraps EasyPost's tracker object in an event envelope it composes, signs it with the integration's secret and posts it to the server. **The tracker came from EasyPost; it was relayed, not delivered.**
  - **Refunds (4.15).** EasyPost's test mode never completes a refund: its own refund list holds only `submitted` and `rejected` refunds, and its event list holds no refund event. The `refund.successful` event that 4.15 relays was **composed by the script** in EasyPost's published shape. It was not sent by EasyPost, and a refund completed by EasyPost is unverified.
- **Deliberate failure.** With Meilisearch stopped and nothing else changed, 4.23 fails, as it should. The failures in §2 show that the other checks' assertions catch a wrong result.

### 1.1 Changes during the development trials

- The payouts checks now wait for the marketplace settings' hint and option before reading them, because a freshly started server showed them a moment late. Their expectations are unchanged.
- The scripts reused a saved marketplace from an earlier trial, which a fresh database no longer holds. The run script now deletes that saved state first.
- EasyPost's test account limits how fast it may be called. A request it limits is retried after a pause, and an order is drafted again until EasyPost's rates have arrived.

### 1.2 After the runs

One comment in `p4-easypost.spec.ts` said that 4.15 relays "the event EasyPost sends". It now says that the event is composed. A blank line that the formatter refused was also removed from `p4-storefront-stripe.spec.ts`. No code or assertion changed.

## 3. Why the storefront's payments are blocked (G-130)

The environment's proxy adds the Stripe secret key to **every** request to `api.stripe.com`, including the requests the shopper's browser makes with the publishable key. A request carrying only a publishable key was answered as if it carried the secret key. Stripe.js confirms a payment with a parameter, `expected_payment_method_type`, that Stripe accepts only from a publishable key. So Stripe refuses every payment the browser sends.

This is the environment, not Spree or the storefront. 4.2, 4.3 and 4.5 pay the same Stripe account successfully from the server.

The checks still assert the intended result and fail at the refusal, which each one records. They can pass only in an approved test environment that meets two conditions:

- Stripe.js's requests keep their publishable-key authentication.
- The backend's calls use the secret key.

The owner directed that they be rerun there, at recorded revisions, with the application and assertions unchanged (§10). G-130 tracks this, separately from OA-8.

## 5. The international label's price

**Unresolved observation.** On 4.14's international label, the buy confirmation quoted $21.86, and Spree recorded the label's postage as $128.03. Both runs show the same figures. EasyPost's own records for both shipments were read back (`evidence/…/label-price.json`):

| | Run 1 | Run 2 |
|---|---|---|
| The rate Spree quoted and bought | `rate_7cfab1c3…`, FedEx International Connect Plus | `rate_88773709…`, the same service |
| That rate in the shipment's rate list | 21.86 (list rate 167.37) | 21.86 (list rate 167.37) |
| `selected_rate.rate` after the purchase, the same rate id | 128.03 | 128.03 |
| Fees EasyPost recorded | postage 21.86, insurance 1.00, label 0.00 | the same |

What this establishes:

- **Spree buys the rate it quoted.** It passes the quoted rate's id to EasyPost's buy call (`SpreeEasyPost::FulfillmentProvider#buy_quoted`). The bought label carries that same rate id, so it is not a mismatch between the quote and the purchase.
- **EasyPost's own answer disagrees with itself.** For one rate id, the rate list and the postage fee say 21.86, but the purchased shipment's `selected_rate` says 128.03. Spree reads the label's cost from `selected_rate.rate`.
- **Domestic labels do not show it.** The domestic USPS label's figures agree everywhere: 6.08.

What it does not establish is whether live mode behaves the same. It looks like EasyPost's test mode re-rating the FedEx label after purchase. If live mode did the same, Spree would show a cost different from the postage charged. It stays an unresolved observation. No live purchase was made.

Every label also carried a 1.00 insurance fee in EasyPost's records, which Spree does not show. This is a second observation.
