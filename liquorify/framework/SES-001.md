# Software Engineering System

A reusable framework for developing, delivering, and operating software. It applies to new projects and existing systems, across one or several repositories. It selects no product, industry, technology, vendor, or deployment model.

This is a draft for adaptation. Adoption establishes the rules for a stated project scope; it does not certify the existing implementation or its controls.

## 1. How to use this system

- Use this document for engineering capability definitions and baseline principles.
- Use the [Engineering Charter](ENG-001-engineering-charter.md) for responsibilities, the SDLC, work handling, and release practices.
- Use the [Documentation System](ENG-002-documentation-system.md) for document ownership, changes, and evidence records.
- Keep product behavior in product requirements and technical choices in designs or decision records.

Apply the capabilities needed by the current work. The catalog is a coverage reference, not a requirement to create 172 documents, teams, tools, or approval steps. Reuse existing mechanisms when they satisfy the current need.

## 2. Domains and responsibility

Each capability has one domain responsible for its meaning. The ID prefix identifies that domain. Project owners assign actual people and contributors through the charter or work item; domain codes are not approval signatures or staffing requirements.

| AE | Application Engineering | 13 | Application implementation and application-facing contracts |
| AR | Technical Architecture | 20 | System boundaries, data, contracts, and consequential technical choices |
| DR | Engineering Delivery | 18 | Source control, builds, integration, releases, and change recovery |
| QV | Quality Engineering | 21 | Verification strategy, trustworthy tests, and evidence |
| SP | Security Engineering | 20 | Security and privacy requirements, controls, and security risk |
| PI | Platform & Infrastructure | 19 | Environments, runtime, infrastructure, and developer tooling |

| **Total** | **Nine domains** | **172** | |

People may hold several responsibilities. Record review limitations where they matter. Security and privacy apply throughout the lifecycle; a domain assignment does not remove another contributor's responsibility to follow the controls.

## 3. Capability catalog

IDs remain stable when wording or file locations change without changing the capability's purpose. A material split, merge, or change of purpose requires an explicit revision and impact assessment. Retired IDs are not reused.

The domain prefix supplies ownership, so the catalog omits repeated owner columns. Contributors are assigned to the actual work rather than prescribed for every capability.

## 4. Assess only what the decision needs

For a feature, release, or engineering improvement, identify relevant capability IDs and record:

- **Scope:** the requirement, change, or release being assessed.
- **Applicability:** required, conditional with its activation condition, or not required for this scope.
- **Current mechanism:** existing code, process, tooling, or operational practice.
- **Finding:** satisfied, partial, gap, dependent on an unresolved decision, requires revalidation, or not assessed.
- **Evidence and limitation:** what was checked, on which revision and environment, and what remains unknown.
- **Next action and owner:** the smallest action needed to resolve the finding.

An unresolved requirement is a decision dependency rather than an assumed implementation gap. A capability outside the current scope may become relevant later. One assessment may cover several capabilities; a small change may record everything in its issue or review.

When describing a control, distinguish its state:

| State | Meaning |
|---|---|
| Planned | Proposed; no implementation claim |
| Configured | A mechanism exists; effectiveness still needs verification |
| Verified | Relevant behavior was demonstrated in an identified context |
| Operating | The mechanism is in recurring use with an owner and current evidence |

These states describe controls, not overall project maturity. An installed package, written policy, or passing build alone does not prove the required outcome.

## 5. Baseline engineering principles

### 5.1 Product and design

Define intended behavior, user flows, failure states, and acceptance criteria before substantial implementation. Reuse an existing design system when suitable. Document necessary extensions, accessibility expectations, and important interaction states. Keep product decisions separate from assumptions inferred from a framework's available features.

### 5.2 Architecture and implementation

Make boundaries, data ownership, contracts, and significant tradeoffs explicit. Prefer small, maintainable changes within the existing architecture. Introduce new services, abstractions, frameworks, or infrastructure when there is a demonstrated need. Handle external failures, retries, duplicates, concurrency, and recovery where the behavior requires them.

### 5.3 Verification and evidence

Choose checks according to affected behavior and risk: static analysis, unit, component, integration, contract, browser, accessibility, visual, performance, resilience, or security checks. Use meaningful assertions and safe representative data. Include permitted and denied cases for access controls.

Evidence identifies the claim, exact revision or artifact, environment, procedure, result, date, and limitation. Results are **PASS**, **FAIL**, **BLOCKED**, or **NOT_RUN**. A check that is not applicable has an explanation; it is not a substitute for a required check. Simulated behavior supports claims about the simulation only.

### 5.4 Security and privacy

Define authentication, authorization, trust boundaries, data protection, secret handling, dependency controls, and security events appropriate to the system. Enforce authorization at service boundaries. Verify separation between users, tenants, and administrative populations where applicable. Limit privileges and sensitive data collection, retention, and logging.

Use isolated development data and authorized external interfaces. Documentation establishes a documented capability; controlled observation establishes behavior in the tested context. Neither justifies broader claims without evidence.

### 5.5 Delivery and recovery

Keep source, dependency resolution, build configuration, and deployable artifacts identifiable. Integrate relevant checks into the delivery workflow. Verify the candidate actually delivered, and use proportionate safeguards for migration and deployment.

Treat application rollback and data recovery as distinct procedures. Specify migration ordering, compatibility, locking, validation, and recovery implications where relevant. Exercise restoration before relying on backups for important data.

### 5.6 Operations and learning

Assign an operational owner, actionable signals, incident handling, and recovery procedures appropriate to the workload. Derive reliability, support, recovery, and cost targets from actual requirements. Feed defects, incidents, user feedback, and operational evidence into the work backlog.

### 5.7 Automation and AI

Automation may investigate, draft, implement, test, review, and execute actions within delegated scope. Accountable people retain authority for consequential product, security-risk, and release decisions. Automated review is identified as such; it is not described as independent human review. Keep credentials and unnecessary sensitive data out of tool output and evidence.

## 6. Change, exceptions, and retirement

Revise affected claims when requirements, trust boundaries, interfaces, schemas, dependencies, configuration, topology, or material incidents change their basis. Preserve historical evidence and add the new result; reassess only the affected scope.

An exception records the unmet obligation, scope, risk, compensating measures, owner, approver, expiry or review trigger, and resolution. An exception does not turn a failed check into a pass. Security exceptions include the responsible security reviewer.

Retirement identifies dependents, replacement or removal plans, data and evidence retention, and verification of safe removal. Ending a particular implementation does not automatically retire the underlying engineering capability.

Changes to this framework follow the [Documentation System](ENG-002-documentation-system.md). Preserve capability IDs and review semantic changes explicitly. Detailed operating procedures remain in the charter to avoid competing definitions.
