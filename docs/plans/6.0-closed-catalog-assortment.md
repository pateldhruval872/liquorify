# Closed Catalog Assortment

**Status:** Implemented — 2026-11-11; the dashboard switch for the flag is a follow-up (Open Questions)
**Target:** Spree 6.0
**Depends on:** B2B Companies & Catalogs (`6.0-b2b-companies-and-catalogs.md`, shipped), Catalog Agreement Rework (`6.0-catalog-agreement-rework.md`, shipped), gated storefront access (`6.0-channels-catalogs-b2b.md` Phase 1.5, shipped 5.6)
**Author:** Liquorify engineering + Claude
**Last updated:** 2026-11-11
**Tracking:** Linear — · GitHub —

## Summary

A channel for approved buyers only has no way to show a signed-in
customer outside its audience nothing. The storefront gate is guest versus
signed-in by design, and the channel plan hands the rest to the catalog:
"give the channel an empty/minimal default catalog". The 2026-08-25
amendment to the companies-and-catalogs plan then made an empty catalog a
pricing-only overlay that restricts nothing, so the empty default catalog
the channel plan recommends now shows such a customer the whole channel
range, and a "minimal" one still shows whatever it holds. The two shipped
plans contradict each other, and neither configuration expresses "members
only".

This plan adds one flag to a catalog, `closed_assortment`. A closed
catalog shows exactly the products it lists, and when it lists none it
shows nothing. An open catalog (the default, and every catalog that exists
today) keeps the amended rule unchanged. A members-only channel is then a
closed, empty default catalog plus a catalog assigned to the members.

## Key Decisions (do not deviate without discussion)

- **The flag is on the catalog, not the channel or the gate.** Catalogs
  decide what a buyer sees; the gate stays guest versus signed-in, as the
  channel plan decided. A per-group gate was rejected because it would make
  customer-group membership an activation mechanism, which the
  self-registration plan rules out.
- **Closed means "exactly this list".** In a buyer's effective catalog set
  a closed catalog contributes its listed products, however many that is.
  An open catalog with an empty assortment still lifts the restriction for
  the whole set, exactly as today. So a buyer whose set holds a closed,
  empty catalog and nothing else sees no products.
- **Open is the default, and nothing existing changes.** The column
  defaults to `false`, so every current catalog, agreement and price
  overlay behaves exactly as the amended plan says. The pricing-only
  overlay stays the meaning of an empty open catalog.
- **Every storefront surface reads the same resolution.**
  `Spree::Products::ForContext` is the one place the flag is read. The
  product listing, product pages, search, wishlist items, cart adds,
  checkout's orderable check and the product filters all narrow through it.
  The product filters do not today: they are narrowed in this plan, with
  the buyer's effective catalogs in their cache key, so facet counts and
  price ranges describe only what the buyer may see.
- **An add from outside the assortment is refused as not found.** That is
  how a curated catalog already refuses one, and a distinct reason would
  confirm to a customer outside the audience that the product exists.
- **The seeded Wholesale channel ships members-only.** Seeds give it a
  closed, empty default catalog, and give the Wholesale group an open,
  empty catalog with no price list, so members keep seeing the whole
  channel range at whatever prices apply to them today.

## Design Details

### Model

`spree_catalogs.closed_assortment` — boolean, `null: false`,
`default: false`. Exposed on the Admin API catalog serializer and accepted
by the Admin catalogs controller's `request_params`; never on the Store
API. `Spree::Catalog#closed_assortment?` is the Rails reader.

### Resolution

`Spree::Products::ForContext`, after `Catalog.for_buyer`:

1. No catalogs: the channel's publications, as today.
2. Any open catalog with an empty assortment: the channel's publications,
   as today.
3. Otherwise: the union of the listed products of every catalog in the
   set. A closed catalog with no products adds nothing, so a set of only
   closed, empty catalogs resolves to no products.

**The audiences do not combine, so an open catalog never reaches a buyer
it was not resolved for.** `Spree::Catalog.for_buyer` walks the company
subtree, then the customer's groups, then the channel's default catalog,
and the first step that finds an active catalog answers alone. A company
member whose company carries a curated catalog is resolved to that catalog
only, even when they are also in a group whose catalog is open and empty,
so rule 2 cannot hand them the whole channel range. A company with no
catalog of its own falls through to the groups, as today.

Pricing and quantity terms are unchanged: they only ever apply to
products a buyer can reach.

### Product filters

`Store::Products::FiltersController#filters_scope` reads through
`storefront_products`, like the listing it describes, and
`filters_cache_key` adds the channel and the buyer's effective catalogs
(`cache_key_with_version` of each), so one buyer's facets are never served
to another.

### Seeds and existing stores

`Spree::Channels::RestrictToMembers` makes a channel members-only for a
customer group: a closed, empty default catalog on the channel and an open,
empty catalog assigned to the group, both activated. It leaves a channel
that already has a default catalog, and a group that already has a
catalog, as they are. `Spree::Seeds::CustomerGroups` calls it when it
creates the Wholesale group, so a new store's Wholesale channel is
members-only. Stores seeded before this get the same through
`spree:channels:restrict_wholesale_to_members`, which changes nothing on a
channel that already has a default catalog.

## Migration Path

1. Migration adding `closed_assortment` to `spree_catalogs`.
2. Resolution change in `ForContext`, with its specs: closed and empty;
   closed and curated; closed beside open and empty; open and empty alone
   (control).
3. Product filters narrowed and re-keyed.
4. Admin API attribute, serializer field, integration spec and OpenAPI
   regeneration; SDK types regenerated.
5. Seeds and the rake task.
6. Developer documentation: `docs/developer/core-concepts/catalogs.mdx`
   explains closed catalogs and the members-only channel.

## Constraints on Current Work

- Do not build "members only" on the storefront gate or on customer-group
  membership; express it with a closed default catalog.
- New storefront surfaces that list products or variants narrow through
  `storefront_products` / `Cart#orderable_variants`, never through the
  store's products directly.

## Open Questions

- The dashboard has no control for the flag in this plan; it is set
  through the Admin API and the seeds. A switch on the catalog page, with
  its end-to-end test, is the natural follow-up.
- `approval_required` (self-registration plan) hides prices and checkout
  from buyers without an active company standing while still letting them
  browse. A closed default catalog hides the products themselves. The two
  compose; whether the seeded Wholesale channel should move to
  `approval_required` once it exists is for that plan.
